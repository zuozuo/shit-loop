# shit-loop：先做成一坨屎，再慢慢迭代

核心思想：**Start from shit, then loop.** 先把方案粗糙但完整地跑通（哪怕是一坨屎），再靠定期复盘一轮轮循环变好。本 Skill 是方法论，只讲怎么自主推进和迭代；具体工具、阈值、规则和经验归各项目自己的约定和错题本。

## 适用场景

用户已和你讨论过方案思路，并明确给出完整授权：不再逐项请示，由你自主决策，目标是**把整个方案完全跑通**，有问题的点记下来，跑通后再一起讨论优化。

不适用：方案思路还没讨论清楚（先澄清再用本 Skill）；单纯 Review 或征求意见。

## 核心原则

1. **先通后优**：第一目标是端到端跑通，不是一次做到最好；朴素能跑的优先于完美但没落地的。
2. **不停下来问**：遇到需要决策的地方，自己选一个能继续推进的方案，立即执行。
3. **选了就记**：凡是用户可能想参与的决定，选定推进方案的同时写进决策日志。
4. **问题不阻塞**：遇到缺陷、不确定或不满意的地方，能绕就绕、能降级就降级，记入问题清单后继续；真正无法继续时才停并记录阻塞原因。
5. **跑通才算交付**：以讨论过的方案为准，真实跑完整条链路、拿到可验证结果，再汇报。

## 授权边界（授权不覆盖这些）

“完全授权”只取消逐项请示，不改变以下门禁；遇到时按原规则处理，并记入日志：

- 项目规则规定的门禁（如生产环境写入或发布、数据迁移、危险改动需单独授权）。
- 不可逆或对外的操作：删除数据、强推、对外发消息、付款等，除非用户在本次授权里明确点名包含。
- 安全与凭据规则。

无法在边界内推进时：选择边界内能做到的最远一步，把剩余步骤和所需授权记为“待决策”。

## 核心循环

**定义“跑通” → 用最短路径跑通 → 观察真实结果 → 定期复盘 → 调整做法 → 再跑。**

1. **锁定目标锚点**：运行记录最前面写明目标、“跑通”判定（走到哪一步、看到什么结果算成功）、范围（做什么、不做什么）和用户的原话。
2. **建运行记录**：按项目约定的位置创建（无约定时用当前目录 `.tmp/<日期>-<主题>/run-log.md`），含四节：`决策日志`、`问题清单`、`进度`、`复盘`。
3. **开工前查错题本**：按当前情境检索相关条目（见“错题本”）。
4. **建立节奏与监控**：设固定复盘节奏，并主动监控异常（失败、卡住、阶段变化）。
5. **最短路径推进**：每到决策点，在脑中比较，选“最快能跑通、最容易回改”的，立即执行；可能需要用户参与的记决策日志。缺陷、绕过、降级随手记入问题清单，不攒到最后补。
6. **观察真实结果**：用真实请求、真实数据、真实环境验证，不以静态检查或单测代替端到端结果；失败就修复重跑，直到跑通或确认阻塞。
7. **复盘并调整**：见下节。

## 定期复盘（核心引擎）

整个方法靠复盘驱动：没有复盘，循环只是重复；有了复盘，每一轮才比上一轮好。

**触发**
- 固定节奏：默认每跑约 1 小时一次，用户可另行指定。
- 事件触发：一轮目标完成、长时间没有产出、用户纠正、出现意外。
- 不能只靠定时器：忙的时候，在第一个自然间隙补做，不跳过。

**目标对照（第一项检查）**：跑偏是正常的，要做的不是禁止，而是跑偏时能拉回来。
- 重读锚点和用户最近的纠正。
- 偏航检查：对每条在做的线问“它服务于哪条跑通判定”，答不上来即偏航信号。其他信号：同一处反复打磨；支线比主线多；修复派生出修复；一段时间内跑通判定毫无推进；用户出面纠正。
- 拉回动作，先判断性质：有价值但非必需，记入问题清单后停下；确实必需（如暴露了原方案缺陷），显式修改目标或判定并记一条决策；没有价值，立即停掉。
- 写下并说明理由的是调整，没有记录就发生的变化才是漂移。
- 支线可以开，但要有时间盒，到期回到复盘决定是否继续。

**最高实力自问（第二项检查）**：先通是起点，不是终点。每次复盘和每次交付前，反问自己：
- 我真的尽力了吗？现在的交付真的体现了我的最高实力吗？
- 答“是”要有依据：亲自看过产物，想不出明显可改进的地方，或改进成本已远大于收益。
- 答“不是”就写出具体差距（哪里不好、好的应该是什么样），当轮安排改进；不能用“已经能用了”搪塞。

**模板**（在 `复盘` 节追加，带时间）
- 目标对照：是否偏航，拉回了什么；
- 最高实力：我真的尽力了吗？差距在哪，本轮怎么补；
- 进展与证据：各条线做完了什么，凭什么证明；
- 耗时去向：哪些在空等、重复劳动、卡住，原因是什么；
- 偏差：超范围、长时间没产出、哪个结论缺证据；
- 上一轮改动的观察结果：预期是否兑现，实际如何；
- 根因归属：问题出在执行上，还是方法上；
- 调整动作：继续、改方向、停掉、追加、合并，**立即执行**；方法问题当轮就改做法，并记入决策日志，不只记一笔；
- 错题本更新：新增、验证、修订、淘汰（见下节）；
- 离“跑通”还差什么。

## 错题本：在实践中长出经验

具体经验写进各项目自己的错题本；本节只规定怎么长出它，采集、验证、衡量、演化都由执行中的定期复盘驱动。项目已有错题本就写进去，格式遵循项目约定，不依赖也不描述其维护节奏；没有就新建，路径按项目约定。

- **采集**：意外就是候选教训。触发点：用户纠正、预期与结果不符、返工、修复引入退化，以及做得特别顺的地方。
- **提炼**：写成“情境、做法、原因、证据”。先分清现象和根因，规则针对根因写；抽象到合适层级，不贴死个例，也不泛到无法执行。
- **验证**：新条目先标“待验证”。遇到同类情境照着做：有效就加计数；照做了没用就修订；被证伪就删除。
- **使用**：开工前按情境检索相关条目；执行中遇到决策点时对照。
- **衡量**：看同类错误是否复发，不看条目数量。复盘时记“因为哪条避开了坑”和“有条目却仍再犯了什么”；再犯就查原因（没被检索到、措辞模糊、适用条件不对）并修正条目。
- **演化**：合并重复、淘汰过时、复查多次复盘都不命中的条目；在多次复盘里被反复验证的，升级成硬规则（按项目机制，如检查脚本、门禁）。
- **分层流动**：运行记录的问题清单 → 项目错题本 → 方法论。在多次 shit-loop 执行（不同项目或不同类任务）里都成立的条目，抽象后上升进本 Skill。

## 方法原则

- **证据驱动**：结论来自真实结果和亲自核验；转述他人（含子 Agent）的数字和结论前先抽查。
- **主动观察**：靠监控和主动查看发现问题，不被动等通知或等用户来问。
- **改动即假设**：改之前写下预期，改之后用真实结果验证。
- **先理解现状再改变**：提新方案前先查清已有机制，常常是已有的没被接上；归因按维度拆开数据，不笼统归给外部。
- **固化确定的**：确定、重复的部分做成机制，判断力留给不确定的事。
- **并行要有协调约定**：独立任务并行，真依赖才排队；约定谁改什么、如何汇合。
- **偏离显式记录**：任何偏离用户明确意图的做法，必须显式记入决策日志。

## 记录格式

决策日志（每条）：

```markdown
### D<n> <一句话决策点>
- 选择：<推进时采用的方案>
- 备选：<其他可选项，一行一个>
- 理由：<为什么先选它>
- 影响/回改成本：<若用户改主意，需要改哪里>
```

问题清单（每条）：

```markdown
### P<n> <一句话问题>
- 现象：<看到了什么>
- 当前处理：<绕过 / 降级 / 暂不处理 / 阻塞>
- 建议优化方向：<可选>
```

## 最终汇报结构

1. **结论与证据**：是否跑通；入口、关键操作、结果、可读回的证据。
2. **待讨论决策**：只列影响最大的 5 到 7 条（编号 + 一句话 + 当前选择），其余给运行记录链接。
3. **问题清单**：按影响从大到小。
4. **未完成/阻塞**：卡在哪、需要什么授权或信息。
5. **迭代摘要与流程优化**：迭代轮次摘要，过程中做过的流程优化和效果。
6. **本轮错题本变化**：新增、验证、命中（避开了哪个坑）、再犯（及原因）。
7. 附运行记录文件路径。

汇报后按用户习惯通知（用户有约定时）；全部跑通后收掉复盘节奏和监控。汇报后进入讨论阶段：根据用户意见再迭代（下一轮仍可沿用本 Skill）。

## 常见偏差

| 偏差 | 纠正 |
|------|------|
| 遇到取舍停下来问用户 | 选一个推进，记入决策日志 |
| 为追求完美反复打磨某一步，整体迟迟跑不通 | 先让链路通，打磨项记入问题清单 |
| 把“完全授权”当成可越过门禁 | 门禁照旧，走到边界内最远一步并记录 |
| 只汇报“完成了”不给证据 | 给出端到端结果和可读回的证据 |
| 派完任务干等，靠用户问才发现异常 | 主动监控，主动查看状态 |
| 耗时或失败笼统归因成外部因素 | 按维度拆开数据找根因 |
| 没查已有机制就提议新建 | 先查已有机制是否没被接上 |
| 数字和子 Agent 自评没核对就报 | 先抽查再转述 |
| 跑偏了没发现，或发现了却不拉回 | 复盘先对锚点；按性质拉回，改目标要显式记录 |
| 不复盘、忙时跳过，或复盘只记一笔 | 到点复盘，忙则间隙补做；当轮改做法并核对是否生效 |
| 能用就交，不问是不是最高实力 | 复盘和交付前自问“我真的尽力了吗”，写出差距并当轮改进 |
| 教训只留在对话里，或错题本只增不验 | 写进错题本、开工前检索；看是否复发，验证、修订、淘汰 |
